# 05 구현과 Task 검증

- **입력** G4를 충족한 Task, 승인된 기대 행동과 검증 명세.

| 변경 | 검증 방식 |
|---|---|
| 결정적 신규 동작·버그 | 기능 코드 변경 전 의도한 실패 확인 → 최소 구현 → 통과 → 필요한 정리와 회귀 |
| Refactor | 변경 전 통과 기준선 → 구조 변경 → 동등성과 회귀 확인 |
| 확률적 AI 동작 | 평가 데이터·기준선·버전·반복 조건 → 변경 → 품질·비용 기준 비교 |

- 환경 오류는 의도한 실패와 구분한다. 승인된 계약·기대값 변경은 해당 결정을 먼저 확인한다. Fixture·환경 수정은 정해진 범위에서 처리한다.
- 테스트 작성 담당이 명세를 실행 가능한 검사로 옮긴다. 결정적 신규 동작·버그는 승인된 기대값으로 의도한 실패와 대상 리비전을 기록한 뒤 구현한다. 담당이 나뉘면 검사 ID, 변경 경로, 명령과 실패 이유를 인계한다.
- 기대 행동이나 독립 근거의 빈틈은 01, 계약·실패 규칙·판정 방법의 빈틈은 해당 03에서 해결한다. 같은 담당이 작업해도 기능 코드 변경 전 근거를 기록한다.
- 신규 경계에서 테스트를 구동할 수 없으면 04에 정한 범위에서 기능 로직 없는 선언·스텁·테스트 환경을 준비한다. 그 상태에서 의도한 실패를 확인한다. 그래도 불가능하면 차단을 기록하고, 대체 증거는 별도로 승인된 예외에서만 사용한다.
- 동작별 검증을 반복한다. 변경 전·후 각각의 리비전, 환경, 명령, 실제 결과와 증거를 기록한다. 기존 실패와 차단 사유를 구분하고 독립 검증에 넘길 리비전을 고정한다.
- **기록** [검증 기록](../../assets/templates/06-verification/verification.md)의 05 섹션과 `tasks.md`의 상태·증거 링크.
- 작은 Task는 계획 행과 코드·검사 링크로 남긴다. 구현 중 결정, 반복 작업 이력 또는 인계가 필요하면 [작업별 구현 기록](../../assets/templates/05-implementation/task-record.md)을 `tasks/<task-id>-<slug>.md`에 둔다. 검사 결과의 정본은 `verification.md`에 두고 링크한다.
- 요구, 아키텍처, 상세 설계나 계약이 달라지면 해당 단계에서 정본과 관련 판정을 갱신한다. 작업별 기록에는 변경 이유와 정본 링크를 남긴다.
