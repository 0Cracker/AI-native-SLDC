# 05 구현과 Task 검증

- **입력** 변경 범위, 확정된 기대 동작 또는 유지할 계약, 관련 검사. 여러 작업을 조율해야 하면 작업 계획을 참조한다.

| 변경 | 검증 방식 |
|---|---|
| 결정적 신규 동작·버그 | 기능 코드 변경 전 의도한 실패 확인 → 최소 구현 → 통과 → 필요한 정리와 회귀 |
| Refactor | 변경 전 통과 기준선 → 구조 변경 → 동등성과 회귀 확인 |
| 확률적 AI 동작 | 평가 데이터·기준선·버전·반복 조건 → 변경 → 품질·비용 기준 비교 |
| 동작 변경 없는 문서 수정 | 변경 내용, 링크 등 수정한 부분 확인 |

- 환경 오류는 의도한 실패와 구분한다. 승인된 계약·기대값 변경은 해당 결정을 먼저 확인한다. Fixture·환경 수정은 정해진 범위에서 처리한다.
- 테스트 작성 담당이 명세를 실행 가능한 검사로 옮긴다. 결정적 신규 동작·버그는 승인된 기대값으로 의도한 실패와 대상 리비전을 기록한 뒤 구현한다. 담당이 나뉘면 검사 ID, 변경 경로, 명령과 실패 이유를 인계한다.
- 기대 행동이나 독립 근거의 빈틈은 01, 계약·실패 규칙·판정 방법의 빈틈은 해당 03에서 해결한다. 같은 담당이 작업해도 기능 코드 변경 전 근거를 기록한다.
- 신규 경계에서 테스트를 구동할 수 없으면 승인된 범위에서 기능 로직 없는 선언, 스텁 또는 테스트 환경을 준비한다. 그 상태에서 의도한 실패를 확인한다. 그래도 불가능하면 차단을 기록하고, 대체 증거는 승인된 예외에서 사용한다.
- 동작별 검증을 반복한다. 변경 전후 리비전, 환경, 명령, 실제 결과와 증거를 기록한다. 기존 실패와 차단 사유를 구분한다. 독립 검증을 수행하는 경우 대상 리비전을 고정해 넘긴다.
- **기록** 작은 작업은 기존 이슈나 PR에 변경 전후 결과와 검사 링크를 남긴다. 별도 기록이 필요하면 [검증 기록](../../assets/templates/verification.md)의 05 섹션이나 [작업별 구현 기록](../../assets/templates/task-record.md)을 사용한다.
- 요구, 아키텍처, 상세 설계나 계약이 달라지면 해당 단계에서 정본과 관련 판정을 갱신한다. 작업별 기록에는 변경 이유와 정본 링크를 남긴다.
- **종료** [G5](../lifecycle.md#단계별-종료-조건)을 확인한다. 적용되는 후속 검증이 있으면 이어서 진행하고, 작업 범위가 충족되면 보고한다.
