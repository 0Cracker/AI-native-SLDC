# 프로젝트 산출물 규칙

- 공통 문서와 변경별 문서는 각각 정해진 루트에 둔다. 기본 경로는 `docs/`와 `specs/<변경 ID>/`다. 변경별 `index.md`는 필수다. 설명이나 리뷰만 요청받아 변경하지 않는 작업은 문서를 새로 만들지 않는다.
- 저장소에 정해진 공통 문서 루트나 변경별 명세 루트가 있으면 해당 구조를 보존하고 대응 경로를 `index.md`에서 명시한다. 정본이 모호하거나 기존 문서를 옮겨야 하면 먼저 확인한다.
- 기존 변경 ID를 재사용한다. 없으면 `F001-short-slug`처럼 충돌하지 않는 ID를 정한다. 이슈, PR, 계약과 검사 기록은 정본으로 재사용하고 `index.md`에서 연결한다. 채팅이나 외부 기록만 남기고 진입점을 생략하지 않는다.
- 같은 변경은 같은 폴더에서 이어간다. 문서 내부에서 Increment를 `INC-01`처럼 구분한다. 신규 파일명은 소문자와 하이픈을 사용하고 기존 ID와 계약 형식을 보존한다.
- 작은 작업은 요구와 설계를 변경 폴더 안의 한 문서로 합칠 수 있다. 단계별 파일을 나누면 아래 경로를 따른다. 적용하지 않는 단계의 빈 문서와 폴더는 만들지 않는다.
- 스킬 평가와 에이전트 운영 기록은 제품 명세 밖의 `evaluation/`에 둔다. 제품 요구, 설계와 검증의 정본을 그곳에 섞지 않는다. 별도 평가를 하지 않는 작업에는 이 폴더가 필요 없다.

## 공통 문서와 변경 기록

- 공통 문서(기본 `docs/`)는 여러 변경에서 참조하는 현재 제품 목표, 공통 구조, 원칙과 결정을 담는다.
- 변경별 명세(기본 `specs/`)는 변경 ID별로 요청, 요구, 설계, 작업 계획과 검증 근거를 묶는다. 공통 정본에는 변경을 통해 확정된 공통 내용만 반영한다.
- 두 루트는 문서의 적용 범위와 보존 기준을 드러내기 위해 나눈다. 프로젝트에서 문서를 한곳에 모으는 경우 `docs/specs/<변경 ID>/`를 변경별 명세 경로로 쓸 수 있다.

## 초기 기록과 명세

- `specs/<변경 ID>/`는 변경별 기록을 모으는 위치다. 변경을 시작할 때 `index.md`를 열고, 00을 적용하면 그 단계부터 요청 근거를 연결한다. 00을 생략하면 처음 선택한 단계의 근거부터 연결한다.
- G0 근거는 기존 이슈 등의 요청 정본에 남긴다. 파일을 분리할 때 기본 위치는 `specs/<변경 ID>/intake.md`다.
- G1에서 동작과 인수 조건을 요구사항 명세로 확정한다. 기존 명세나 이슈를 재사용할 수 있다. 파일을 분리할 때 기본 위치는 `specs/<변경 ID>/requirements/R001-*.md`다.
- G2의 변경별 구조 결정은 분리할 때 `specs/<변경 ID>/architecture/A001-*.md`에 둔다. 여러 변경에 적용할 제품 방향과 공통 아키텍처는 프로젝트 공통 정본(기본 `docs/`)에서 관리한다.

## 변경 단위와 상태

- **기존 ID를 이어간다** 같은 목표와 인수 범위를 마무리하는 작업이다. 구현 보완, 검증 실패 수정, 재개와 내부 Task나 Increment 분할은 기존 ID 아래에서 진행한다.
- **새 ID를 만든다** 기존 변경을 먼저 인수하거나 완료한 상태에서도 별도로 인수하거나 보류할 수 있는 목표와 조건이 생긴 경우다. 완료 뒤 발견한 별도 결함이나 새 요구는 새 ID에서 원래 변경을 연결한다. 완료 기록의 오기 정정은 기존 기록에서 원래 판정과 구분한다.
- 같은 목표라면 대화, 담당자, PR, 커밋이 나뉘어도 ID를 이어간다. 예를 들어 CSV 내보내기의 합의된 필터 동작을 검증 중 고치는 일은 기존 ID를 쓴다. CSV를 먼저 인수하고 별도로 예약 발송을 결정할 수 있으면 예약 발송에 새 ID를 만든다.
- 상태는 `진행 중`, `보류`, `완료`, `취소`로 구분한다. 보류는 이유와 재개 조건, 취소는 이유와 남은 코드나 데이터의 처리 상태를 적는다.
- 변경 목록은 기존 이슈 관리 도구를 우선한다. 없으면 변경별 명세 루트의 `index.md`에 ID, 상태와 링크만 둔다. 기본 경로는 `specs/index.md`다. 완료 폴더를 별도로 이동할 필요는 없다.

## 기록 보존과 정리

- 현재 제품 명세는 `docs/`의 정본에 확정된 동작과 결정만 반영한다. 변경별 기록을 통째로 복사하지 않는다.
- 완료 기록은 당시 범위, 대상 버전과 판정 근거를 보존하고 후속 변경을 연결한다. 기록 오류의 정정은 원래 판정과 구분한다.
- 종료 시 필요한 결정과 인계를 정본에 반영한 뒤 임시 메모와 불필요한 중복 자료를 정리한다. 인수, 복구와 재현에 필요한 증거는 보존한다.
- 큰 로그와 화면 원본은 프로젝트의 별도 저장소와 보존 정책을 따르고 근거 링크를 유지한다. 정책 없이 기간을 정해 자동 삭제하지 않는다. 실제 저장 데이터와 비밀정보는 문서 보관 대상으로 취급하지 않는다.

## 필수 진입점

- `index.md`는 변경 ID와 현재 상태를 먼저 쓰고, 정본 위치, 선택한 단계, 생략한 단계와 이유, 대상 코드 버전과 검증 근거를 링크와 짧은 상태표로 연결한다. 생략 단계는 같은 이유끼리 묶을 수 있다.
- 본문, 상세 계약, 인수 조건, 작업 이력과 로그를 복제하지 않는다. 기존 이슈나 PR이 정본이면 링크로 충분하다. 파일은 상대 링크, 외부 기록은 접근 가능한 링크로 연결한다.
- 결과가 여러 Increment나 버전에 걸치면 각 범위와 판정 근거를 구분해 연결한다. 이전 결과는 정본에 보존하고, 진입점에는 현재 상태와 다음 작업 또는 차단 조건만 짧게 표시한다.
- 완료와 인계 전에 링크를 실제로 열거나 파일 존재를 확인한다. 다음 담당이 대화 없이 정본, 현재 상태와 검사 결과를 찾을 수 있어야 한다.

## 폴더 구조

`index.md`만 모든 변경에 필수다. 나머지는 필요한 산출물의 지정 위치이며, 아래 파일을 모두 만들라는 뜻이 아니다.

```text
docs/                              # 여러 변경에 적용하는 현재 프로젝트 공통 문서
├── product.md                     # 제품 목표와 대상 사용자
├── constitution.md                # 공통 원칙과 품질, 승인 기준
├── architecture.md                # 현재 시스템의 공통 경계, 구성요소, 책임
├── tech-stack.md                  # 공통 기술 스택과 제약
├── glossary.md                    # 여러 변경에서 쓰는 공통 용어
├── decisions/                     # 중요한 결정의 대안과 선택 이유
│   └── ADR-*.md                   # 결정 하나의 근거와 영향
└── diagrams/                      # 여러 변경에서 참조하는 시스템 공통 그림

specs/                             # 변경별 명세와 당시 판단 근거
├── index.md                       # 변경 목록, 기존 이슈 관리 도구가 없을 때
└── F001-short-slug/               # 함께 인수할 변경 범위 한 건
    ├── index.md                   # 이 변경의 상태와 정본, 검증 링크
    ├── intake.md                  # 요청의 목표와 범위, 착수 조건
    ├── requirements/              # 보장할 동작과 인수 조건
    │   └── R001-short-slug.md      # 인수 판단 단위의 요구사항
    ├── architecture/              # 이번 변경이 영향을 주는 구조와 경계
    │   ├── A001-short-slug.md      # 구조 결정 하나와 시스템 검증 기준
    │   └── diagrams/              # 이번 변경의 구조와 경계를 보여 주는 그림
    ├── designs/                   # 구현에 필요한 동작, 상태, 오류 처리
    │   ├── D001-short-slug.md      # 구현과 검증을 위한 상세 설계 단위
    │   └── diagrams/              # 상세 동작과 데이터, 상태 전이를 보여 주는 그림
    ├── contracts/                 # 호출자와 구현이 공유할 API, 이벤트 등의 정형 계약
    ├── tests/                     # 이 변경의 검증 계획과 기대값 근거
    │   ├── test-plan.md           # 실행할 검사와 판정 기준
    │   └── golden/                # 필요한 경우 사용하는 독립 기대값 자료
    ├── tasks.md                   # 작업 목록과 순서, 의존성, 진행 상태
    ├── tasks/                     # 필요한 경우 남기는 개별 작업의 실행 기록
    │   └── T001-short-slug.md      # 한 작업의 실제 변경, 검증 근거와 인계
    ├── verification.md            # 실제 검사 결과, 대상 버전과 판정 근거
    ├── spike-report.md            # 가설 검증과 기술 타당성 실험 결과
    ├── release.md                 # 이 변경의 배포와 복구 기록
    ├── operations.md              # 배포 후 운영 관측과 후속 결정
    └── reports/                   # 요청이나 프로젝트 규칙에 따른 HTML 보고서
```

| 경로 | 정본과 생성 시점 |
|---|---|
| `index.md` | 필수 진입점. 정본 링크, 단계 선택과 생략 이유, 현재 상태, 대상 버전과 검증 근거만 짧게 연결 |
| `intake.md` | 00 요청, 목표, 포함 범위와 제외 범위와 착수 판단 |
| `requirements/R001-*.md` | 01 요구 하나, 시나리오, 인수 조건과 기대값 근거. Intake와 관련 요구 연결 |
| `architecture/A001-*.md` | 02 영향을 받는 경계나 구조 결정 하나. 관련 요구와 구조 의존성 연결 |
| `designs/D001-*.md` | 03 구현·검증할 상세 설계 단위 하나. 관련 구조 결정과 요구·검사 연결 |
| `architecture/diagrams/A001-*.mmd`, `designs/diagrams/D001-*.mmd` | 단계별 편집 가능한 그림 원본. 공통 그림은 공통 문서 루트 |
| `contracts/` | 변경 API·이벤트·Tool의 정형 계약 또는 기존 정본 참조 |
| `tests/test-plan.md`, `tests/golden/` | 검증 명세, 필요시 허용된 독립 기대값. 실행 테스트는 저장소의 기존 경로 |
| `tasks.md` | 04에서 조율할 작업의 목록, 순서, 담당, 의존성, 완료 조건과 검사 ID를 정리한다. 05에서 상태와 근거 링크를 갱신한다. |
| `tasks/<task-id>-<slug>.md` | 05에서 특정 Task의 실제 변경, 결정 이유, 검증 근거, 인계를 별도로 추적할 때 사용한다. `tasks.md`의 해당 작업 행에 연결한다. |
| `verification.md` | 05 작업 검증의 증거와 06에서 적용한 통합, 인수 조건, 품질, 회귀, 독립 검증 결과의 정본 |
| `spike-report.md`, 공통 `decisions/ADR-*.md` | 실험 기록, 중요한 구조 결정 |
| `release.md`, `operations.md` | 07 배포·복구, 08 운영 관측과 결정. 적용 시 작성 |
| `reports/` | 사용자 요청이나 프로젝트 규칙에 따라 HTML 보고를 보관할 때 사용한다. 기존 경로를 우선하고 [작성 가이드](stage-report.md)를 따른다. |

- 기존 정본과 ID를 재사용한다. 필요한 폴더와 문서만 만들고 이관은 먼저 확인한다.
- 요구는 인수 판단 단위, 아키텍처는 경계·구조 결정 단위, 상세 설계는 동작·계약 단위로 나눈다. 03의 A~H와 확장 영역 이름은 `A001`·`D001` 같은 문서 ID와 구분한다.
- 각 문서가 상위 근거를 ID와 상대 링크로 가리킨다. 한 문서에서 여러 상위 근거를 참조할 수 있다. 문서 분리 여부와 관계없이 `index.md`에서 정본과 검증 근거를 찾을 수 있어야 한다.
- 작성 틀은 [단계별 플레이북](lifecycle.md), [03 세부 가이드](playbooks/03-detailed-design.md)에서 고른다. [작성 근거와 한국어 규칙](template-sources.md)을 참고한다.
- [템플릿](../assets/templates/)에서 선택한 단계에 필요한 작성 틀을 찾는다. 구현과 검증은 같은 검증 기록을 사용할 수 있다.
