# 변경 영향에 따른 작업 예시

요청 범위, 기존 계약, 데이터·권한·운영 위험을 기준으로 필요한 단계와 증거를 고른다. 아래 예시에 영향을 더하거나 빼서 실제 작업에 맞춘다.

모든 변경은 [산출물 규칙](artifact-layout.md)에 따라 변경별 `index.md`를 유지한다. 아래의 기존 이슈, PR과 검사 결과는 정본으로 연결하고 본문을 중복 작성하지 않는다.

| 변경 유형 | 적용할 작업과 단계 | 완료 근거와 기록 위치 |
|---|---|---|
| 오탈자, 문장, 링크 수정 | 바로 수정하고 바뀐 내용과 링크를 확인한다. | 변경별 `index.md`에서 수정 정본과 확인 근거를 연결한다. |
| 새 프로젝트의 첫 출시 | 문제와 첫 출시 범위는 00, 인수할 동작은 01, 새 구조와 시스템 검증 방법은 02에서 정한다. | 공통 제품 방향과 구조는 공통 문서, 첫 출시의 변경별 근거는 변경 기록에 둔다. |
| 기존 서비스의 CSV 내보내기 추가 | 대상과 범위가 분명하면 00을 생략한다. 출력 필드와 접근 조건은 01, 기존 구조 안의 파일 포맷 설계는 필요 시 03을 적용한다. 대용량 처리를 위해 큐와 워커 책임을 새로 정하면 02도 적용한다. | 요구, 설계, 검사를 변경별 정본에 연결한다. |
| 기존 계약을 유지하는 작은 버그 | 05에서 재현, 의도한 실패 확인, 수정, 회귀 검사를 진행한다. 구성요소 간 연결에 영향이 있으면 06에서 통합 검증을 한다. | 기존 계약이나 이슈를 기대값 근거로 삼는다. 변경 전후 결과는 기존 이슈나 PR에 합쳐 기록한다. |
| 동작을 유지하는 작은 리팩터링 | 05에서 통과 기준선을 확보한 뒤 동등성과 회귀를 확인한다. 책임이나 의존성이 바뀌면 관련 설계를 추가한다. | 유지할 계약과 검사 결과를 기존 이슈나 PR에 기록한다. |
| API·권한 등 계약 변경 | 미결 동작은 01, 영향받는 구조와 계약은 02 또는 03에서 결정한다. 05에서 구현하고 필요한 통합과 인수 조건을 06에서 확인한다. | 변경된 계약과 호환성·권한 검사 결과를 기존 정본과 PR에 연결한다. |
| 운영 DB 이행 | 03에서 데이터와 복구를 설계하고, 05와 06에서 실행 절차와 무결성을 검증한다. 배포를 맡았다면 07에서 권한·중단·복구와 배포 후 상태를 확인한다. | 리허설, 적용 버전, 무결성 대조와 복구 검사 결과를 이행 기록이나 기존 배포 기록에 남긴다. |

- 기존 기록으로 충분한 작은 작업은 `index.md` 외에 별도 사양, 그림, 단계별 문서나 HTML을 추가하지 않는다. 복구 위험이나 계약 영향이 새로 드러나면 관련 단계와 검사를 추가한다.
- 적용되는 [종료 조건](lifecycle.md#단계별-종료-조건)은 유지한다. 필수 검사나 결정이 빠졌으면 차단이나 미검증 상태를 남기고, 예외는 승인 범위와 대체 근거를 기록한다.
