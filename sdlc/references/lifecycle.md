# 단계 선택과 종료 조건

- 아래 표에서 요청과 변경 영향에 해당하는 단계만 선택한다. 필요한 선행 결정과 증거는 현재 범위에 유효한 계약, 테스트, 이슈나 PR에서 가져오거나 보강한다. 단계별 판정은 같은 기록에 합칠 수 있다. 작은 변경은 [작업 예시](compact-routes.md)를 참고한다.
- Spike·PoC는 실험 기록과 반영 판단으로 종료한다. 제품에 반영할 때 실험 근거를 재사용하고 제품 변경의 영향을 다시 판단한다. 긴급 안정화는 부여된 사고 대응 권한에 따라 실행하고 근거를 남긴다. 신규 수정의 배포에는 관련 제품 검증과 배포 준비 조건을 적용한다.
- 재개하거나 상위 결정이 바뀌면 [재개와 재검증](resume-and-recheck.md)에 따라 영향받은 증거만 다시 확인한다. 테스트 문제는 기대값 근거와 검사 방식의 원인을 나눠 복귀한다.
- 판정은 통과·실패·차단·승인된 예외로 기록한다. 승인된 예외는 승인 범위와 대체 증거, 잔여 위험을 남긴다. 승인에 다음 단계 진행이 포함되고 나머지 기준을 충족할 때만 진행한다. 승인 범위를 넘으면 차단한다. 미실행 검사는 통과로 집계하지 않는다.

## 변경 전체 종료

- 단계 통과와 변경 완료는 구분한다. 요청 범위와 적용 단계의 종료 조건을 충족하고, 필요한 검사와 현재 제품 명세 반영을 마친 뒤 완료한다. 요청된 배포나 운영 작업이 남으면 완료가 아니다.
- 미검증과 잔여 문제는 해결, 후속 변경, 승인된 보류나 예외로 처리하고 근거를 연결한다. 필수 검사의 실패나 차단이 남으면 승인된 예외 없이 완료하지 않는다.
- [기록 정리](artifact-layout.md#기록-보존과-정리) 후 `index.md`의 상태, 대상 버전과 증거 링크를 확인한다. 보류와 취소는 완료로 집계하지 않는다.

## G0, G1, G2의 범위

판정 대상은 이번에 착수하거나 수락할 범위다. 새 프로젝트에서는 최초 출시 범위에, 기존 프로젝트에서는 해당 기능, 버그, 리팩터링 범위에 같은 기준을 적용한다. 제품 목표, 공통 원칙, 기존 아키텍처는 프로젝트 공통 기준으로 참조하고, 그 기준 자체가 바뀔 때 갱신한다.

- G0는 해결할 문제와 이번에 다룰 범위, 착수를 좌우하는 위험과 권한을 확인한다. 성공 목표는 결과 수준으로 잡는다.
- G1은 그 범위에서 사용자나 호출자가 관찰할 동작과 인수 조건, 기대값 근거를 확정한다.
- G2는 G1의 요구를 충족할 구조와 시스템 수준 검증 방법을 결정한다. 기존 구조 안의 세부 계약이나 동작 설계가 필요하면 03을 선택한다.

이미 유효한 요청, 요구, 구조 결정이 있으면 근거를 재사용한다. 이번 변경에서 새로 판단할 단계부터 시작하고 필요한 판단은 합쳐 진행할 수 있다. [기록을 시작할 시점과 저장 위치](artifact-layout.md#초기-기록과-명세)를 참고한다.

## 단계별 종료 조건

선택한 단계의 조건을 확인하고 증거를 대상 범위나 리비전에 연결한다. 중요한 미결은 [인터뷰 규칙](planning-interview.md)에 따라 확인한다. 필수 증거가 부족하면 원인과 해소 조건을 남긴다.

| 단계와 판정 | 적용 조건 | 종료 조건과 증거 | 미충족 시 |
|---|---|---|---|
| [00 요청 정의](playbooks/00-intake.md) **G0** | 문제, 목표, 포함 범위와 제외 범위, 착수 위험이나 권한을 정해야 할 때 | 이번 변경의 범위, 성공 목표와 착수 조건을 기록한다. | 목표와 범위 확인 |
| [01 요구사항](playbooks/01-requirements.md) **G1** | 새 동작을 추가하거나 의도된 동작 또는 인수 기준을 확정하거나 변경할 때 | 정상과 예외, 유지할 계약, 인수 조건과 기대값 출처를 연결한다. | 기대 동작과 근거 확인 |
| [02 아키텍처](playbooks/02-architecture.md) **G2** | 시스템 경계, 구성요소 책임, 의존성이나 주요 시스템 품질 위험을 새로 결정하거나 바꿀 때 | 구조 결정과 절충, 검증할 시스템 시나리오를 기록한다. 필요하면 그림을 연결한다. | 구조 보강 또는 타당성 실험 |
| [03 상세 설계](playbooks/03-detailed-design.md) **G3** | 계약, 데이터, UX, 권한, 복구 등 구현 전에 결정할 영향 영역이 있을 때 | 해당 영역의 정상과 실패 동작, 계약, 검사를 연결한다. 통합이 필요하면 검사와 실행 조건을 정한다. | 관련 설계나 검사 보강 |
| [04 작업 계획](playbooks/04-task-planning.md) **G4** | 작업 간 의존성, 인계 또는 통합 순서를 조율해야 할 때 | 작업 범위, 담당, 의존성, 완료 조건과 검사 배정을 기록한다. | 담당과 실행 준비 확인 |
| [05 구현](playbooks/05-implementation.md) **G5** | 변경을 구현할 때 | 변경 종류에 맞는 기준선과 수정 후 결과, 관련 회귀를 대상 코드와 연결한다. 동작 변경 없는 문서는 변경 부분을 확인한다. | 원인 수정 후 영향 검증 |
| [06 검증 및 통합](playbooks/06-verification.md) | 구성요소 간 연결이나 경계 계약에 영향이 있거나, 여러 작업의 결과 또는 변경 전체의 인수 조건을 확인해야 할 때 | 대상 리비전과 환경, 적용한 통합, 인수 조건, 품질, 회귀, 독립 검증의 결과와 근거를 기록한다. | 원인에 해당하는 계약, 설계, 구현 또는 검사를 보강하고 영향 범위를 재검증한다. |
| [07 배포](playbooks/07-release.md) **Ready 배포 전** | 이행·배포 준비나 실행이 요청 범위일 때 | 검증된 버전, 권한, 환경·설정, 호환성과 이행, 중단·복구·관측 준비를 확인한다. | 준비 보완 후 재판정 |
| **G7 배포 후 정상** | 실제 배포 후 | 배포 버전과 환경을 확인하고 핵심 흐름, Smoke 검사, 관측 결과를 기록한다. | 중단·안정화 후 수정과 재검증 |
| [08 운영](playbooks/08-operations.md) **G8 운영 결정** | 운영 관측이나 후속 결정이 요청 범위일 때 | 기준선 또는 부재 사유, 관측 기간과 결과, 후속 결정과 담당을 기록한다. | 근거를 보강하고 재판정 |
