# SDLC

- 요청 범위, 프로젝트 지침, 기존 계약과 테스트를 확인한다. 설명과 리뷰 요청은 해당 조사와 보고로 마친다.
- [단계 선택 기준](references/lifecycle.md)과 [작업 예시](references/compact-routes.md)를 바탕으로 변경 영향, 불확실성, 복구 난이도에 맞는 단계만 고른다. 단계는 신규 프로젝트 전체 또는 기존 프로젝트의 이번 변경 범위에 적용한다. 단계 번호는 플레이북 식별자다. 선택한 단계는 합쳐 진행할 수 있고, 새 영향이 드러나면 필요한 단계만 추가한다.
- 기대 동작과 범위가 명확하면 수정과 검증으로 바로 진행한다. 중요한 미결은 [인터뷰 규칙](references/planning-interview.md)에 따라 확인한다. 범위가 같은 기존 결정은 재사용한다.
- 선택한 단계의 [종료 조건](references/lifecycle.md#단계별-종료-조건)을 적용한다. 동작 변경은 변경 전후 근거와 관련 회귀 결과를 확보한다. 동작을 바꾸지 않는 문서 수정은 내용과 링크 등 변경 부분을 확인한다. 필수 검사를 실행하지 못했으면 이유와 미검증 상태를 남긴다.
- 변경 작업은 [산출물 구조](references/artifact-layout.md)를 반드시 확인하고 따른다. 공통 문서는 `docs/`, 변경별 기록은 `specs/<변경 ID>/`에 두고 변경마다 `index.md`를 유지한다. 기존 프로젝트의 문서 루트와 정본은 보존하고 `index.md`에서 연결한다. 단계와 문서 수의 축약은 기록 위치와 진입점의 생략을 뜻하지 않는다.
- 새 변경을 만들기 전에 같은 목표의 기존 변경을 확인한다. [변경 단위와 기록 관리](references/artifact-layout.md#변경-단위와-상태)에 따라 ID를 재사용하고, 종료할 때 현재 명세와 보존할 근거를 정리한다.
- 프로젝트가 쓰는 이슈, PR, 계약, 테스트와 문서는 정본으로 재사용한다. 복잡한 관계를 설명하거나 검토할 때 [그림 규칙](references/diagram-policy.md)을 참고한다.
- 프로젝트의 권한과 승인 규칙을 따른다. 인수, 배포 정상, 운영 결과는 각각 판정한다.

## 문서 작성 공통 규칙

- 이 스킬로 작성하거나 갱신하는 명세, 설계, 작업 기록, 검증과 보고에 공통 적용한다. 첫 문장에 결론, 결정 또는 현재 상태를 쓰고 필요한 근거와 조건을 뒤에 둔다.
- 짧은 개요식으로 쓴다. 한 항목에는 한 가지 판단이나 사실을 담고, 비교와 상태는 간단한 표로 정리한다. 불필요한 배경과 진행 경과, 중복 요약은 생략한다.
- 판단에 필요한 요구, 이유, 위험, 예외, 수치와 단위, 불확실성, 대상 버전과 검증 근거는 보존한다. 긴 로그와 원문은 복사하지 않고 경로와 관련 위치를 연결한다.
- 같은 내용은 정본 한 곳에만 쓰고 다른 문서에서 참조한다. 템플릿은 필요한 항목만 사용하고, 해당 없는 항목과 빈 절은 제거한다. `index.md`는 링크와 짧은 상태표로 제한하며 정본 본문을 반복하지 않는다.

## 마감 보고

- 기본은 작업 마지막에 채팅이나 기존 이슈·PR에 한 번 보고하는 것이다. 변경, 검증 결과와 근거, 미검증·차단 사항을 독자에게 맞는 말로 간단히 정리한다.
- 중요한 결정이나 승인이 필요하거나 진행이 막히면 중간에 공유한다. 사용자 요청이나 프로젝트 규칙에 따라 HTML 보고를 작성할 때만 [HTML 작성 가이드](references/stage-report.md)를 읽는다. 보고 시점과 범위도 해당 요청이나 규칙을 따른다.
